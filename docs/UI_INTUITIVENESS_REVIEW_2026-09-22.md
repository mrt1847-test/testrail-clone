# 화면의 직관성 재검토 — 2026-09-22

> **2026-09-23 보완:** 이 개별 문제 목록만으로 페이지 UI/UX 검토를 완료한 것으로 보지 않는다. [공식 화면과 페이지 전체 구성 비교](./TESTRAIL_PAGE_COMPOSITION_REVIEW_2026-09-23.md)를 상위 판단으로 적용한다. 특히 UX-R15의 차트 우선 배치에 대한 강한 평가는 해당 문서에서 범위를 정정했다.

기준: 테스터가 경로·버튼·정책 설명을 해석하거나 이전 조작을 기억하지 않아도 **구조, 현재 범위, 대상, 다음 행동, 처리 상태**를 알아볼 수 있는가. 기능이 실행된다는 사실은 이 검토의 합격 근거가 아니다.

[주 보고서](./E2E_USABILITY_REVIEW_2026-09-21.md)의 UX-R01~10을 보완한다. 이번에 실제 캡처 18개를 다시 열어 시각 검토했고 일부 표현은 소스로 대조했다. 캡처는 9월 21일 격리 환경에서 직접 조작한 결과다. 9월 22일 새 실행이나 TestRail 실서비스와의 동시 비교는 하지 않았다. 원본 hash 대조에서 drift 0을 확인했다. 사용자 오해는 관찰된 사실과 구분해 위험으로 적었다.

## UX-R11 — 전체 범위와 선택 섹션의 시각적 의미가 충돌함 · P1

**화면:** [All sections](./ux-evidence/e2e-0921-scope-all.png). 왼쪽 Login은 파란색으로 선택되고, 본문 상단 경로는 Commerce / Login, 검색 옆 제목도 Login이다. 범위 선택만 All sections이며 본문 첫 블록은 Commerce다.

**직관성 문제:** 사용자는 선택 강조와 제목을 '현재 보고 있는 목록'으로 읽기 쉽다. 이 화면에서는 전체 조회와 트리 포커스가 별개라 어느 표시를 믿어야 할지 판단해야 한다. 전체 범위에서도 트리 포커스를 유지하는 기능은 가능하지만 그 차이가 화면에 드러나지 않는다. `CaseListPane.tsx` 역시 all에서 `setTreeFocusSection`과 목록 조회 범위를 분리한다.

**개선 방향:** 본문 제목은 실제 조회 범위를 나타내고, 트리에서 가리키는 위치는 별도의 이동/포커스 표현으로 구별한다. 전체 범위에서 한 섹션이 조회 대상으로 선택된 듯한 강조를 그대로 쓰지 않는다. 설명 문단 추가로 해결하지 않는다.

**검증:** all에서 다른 섹션을 가리킨 뒤 '현재 어떤 TC가 표시되는가'를 화면만 보고 답할 수 있어야 한다. direct/subtree에서는 제목·강조·실제 목록 범위가 맞아야 한다. UX-R10 계층 표시와 함께 검토하되 조회 정책을 임의 변경하지 않는다.

## UX-R12 — 일괄 선택과 단일 상세가 동시에 행동 대상으로 보임 · P1

**화면:** [6개 선택](./ux-evidence/e2e-0921-bulk-select.png). 가운데는 6 selected·Passed·Apply result·Assign, 오른쪽은 C5·Add result·Pass & Next·Assign to me, 상단에는 Run의 Assign과 또 다른 Pass & Next가 있다.

**직관성 문제:** 사용자는 '지금 선택한 6개'와 '열어 둔 C5'를 구별한 뒤 버튼의 적용 범위를 추론해야 한다. 모두 같은 화면에서 활성화되어 있고 비슷한 동사가 반복된다. 실제 잘못된 일괄 저장을 관찰한 것은 아니다. 대상 혼동 위험은 캡처로 확인할 수 있다.

**개선 방향:** 일괄 작업 영역은 선택 수와 적용 대상을 행동 가까이에 명시한다. 단일 상세의 기록 동작은 C5에 대한 행동임을 분명히 하고 일괄 모드와 시각적으로 경쟁하지 않게 한다. Run 담당자·선택 테스트 담당자·현재 테스트 담당자는 적용 대상이 다르다는 점을 드러낸다. 무조건 단일 상세를 제거하지 않는다.

**검증:** 체크한 6개와 열어 둔 1개가 다를 때, 클릭 전에 각 결과/할당 버튼의 대상을 지목할 수 있어야 한다. 선택 해제·필터 변경·화면 밖 선택·모바일에서도 확인한다. UX-R05의 버튼 수 정리보다 대상 구별을 우선한다.

## UX-R13 — 부분 성공 상태에서 버튼이 다음 행동을 설명하지 못함 · P1

**화면:** [첨부 실패](./ux-evidence/e2e-0921-attachment-partial.png). Result saved 문구가 있지만 가장 강조된 버튼은 Add Result로 남아 있다. 파일 옆 Retry와 footer Retry가 함께 보이고, Cancel도 남아 있다. [이탈 확인](./ux-evidence/e2e-0921-attachment-leave-dialog.png)은 Keep editing / Leave / Discard unfinished를 제시한다.

**직관성 문제:** '결과는 저장됐고 파일만 남았다'는 상태를 읽어 이해해도 Add Result가 재저장인지 재시도인지 예측하기 어렵다. Cancel이 저장 결과를 취소하는지, Discard unfinished가 파일만 버리는지 버튼만으로 알기 어렵다. 기존 재시도에서 결과 수가 유지된 기능 검증은 이 혼란을 해소하지 않는다. 여기서는 Add Result 재클릭이 중복 결과를 만든다고 단정하지 않는다.

**개선 방향:** 저장 완료와 첨부 실패를 구분하고 현재 남은 행동을 '첨부 재시도', '저장된 결과로 돌아가기' 등 대상이 드러나는 말로 표현한다. 파일별/전체 재시도가 둘 다 필요하면 적용 범위를 구별한다. 저장 이후 종료는 저장 전 Cancel과 다른 의미로 보여야 한다. 실패한 첨부를 버릴 때 이미 저장된 결과가 유지됨을 명확히 한다.

**검증:** 실패 직후 '무엇이 저장됐나 / 무엇을 다시 하나 / 닫으면 무엇이 남나'를 답할 수 있어야 한다. 전체 저장 실패·단일 첨부 실패·여러 파일 중 일부 실패·재시도 성공의 문구와 행동을 구분한다. 결과 정책 변경이나 저장소 추가 작업으로 확대하지 않는다.

## UX-R14 — 실행 가능한 Plan에 미완료 설정처럼 보이는 표현이 앞섬 · P2

**화면:** [Plan](./ux-evidence/e2e-0921-resume-plan.png). Runs to execute 아래 NO CONFIGURATION이 가장 먼저 나오고 오른쪽에 Configure, 아래에는 Open run이 있다. breadcrumb는 긴 숫자 ID, 요약은 generated runs / entries라는 용어를 쓴다.

**직관성 문제:** 구성 조합이 없는 정상 Run도 아직 설정을 끝내지 않은 상태로 읽힐 수 있다. 실행자는 Configure를 먼저 해야 하는지 판단해야 한다. 'NO CONFIGURATION' 출력은 `PlanDetailPage.tsx`의 구성 이름 없는 행에서 확인했다. 실제 초보자가 멈췄다는 주장은 아니다.

**개선 방향:** 정상적인 구성 없음과 필수 설정 누락을 구별한다. 실행 가능한 Run은 실행 진입과 실행 대상을 우선하고 구성 관리·내부 ID는 보조 정보로 둔다. entry 자체를 삭제하거나 Plan 구조를 숨기지 않는다.

**검증:** 구성 조합 없음/있음, 아직 Run이 없는 entry를 나란히 놓고 즉시 실행 가능한 것을 구별해야 한다. memory 환경의 Plan 집계 오류는 별도 기능 결함이므로 이 표현 문제의 근거로 혼합하지 않는다.

## UX-R15 — 업무 재개 화면에서 실제 업무보다 요약이 먼저 보임 · P2

**화면:** [Overview](./ux-evidence/e2e-0921-resume-overview.png)의 Active work는 차트 아래 y≈500에서 시작한다. [Milestone](./ux-evidence/e2e-0921-resume-milestone.png)은 제목/관리·통계·같은 진행률 반복·일정 없는 Forecast 영역이 초기 화면을 차지한다. 실제 Run 목록은 이 캡처에 보이지 않지만 All linked runs 바로가기는 있다.

**직관성 문제:** '하던 테스트를 계속한다'는 목적에서는 다음 작업보다 요약을 먼저 훑어야 한다. Milestone에는 일정이 없는데도 비교적 큰 Forecast 안내가 남는다. 단, 관리자에게 요약 화면이 필요한 것은 정당하므로 모든 차트를 제거하자는 판정은 아니다.

**개선 방향:** 실행 재개 항목 또는 연결 Run 진입을 빠르게 발견할 수 있게 하고, 정보 없는 차트/예측과 중복 진행률의 점유를 줄인다. 실행 업무와 관리 요약의 우선순위를 화면 목적에 맞춘다.

**검증:** 미실행·차단·기한 임박 상황에서 다음에 열 업무를 선택할 수 있는지 확인한다. 데이터가 충분한 요약과 비어 있는 요약 모두 비교한다. 현재 캡처는 작은 fixture이므로 대규모 목록에서의 성능·효율까지 합격 처리하지 않는다.

## UX-R16 — 단계별 기대 결과와 공통 기대 결과의 구분이 약함 · P2

**화면:** [작성 중 취소 확인 배경](./ux-evidence/e2e-0921-cancel-dialog.png)에 step 1의 Action / Expected 다음으로 Expected result가 이어진다. [템플릿 변경](./ux-evidence/e2e-0921-template-warning.png)에서는 공통 expected outcome이라는 설명을 읽어야 두 개념이 연결된다.

**직관성 문제:** 거의 같은 명칭의 두 입력 위치가 있어 어느 곳에 검증 기준을 써야 하는지, 중복 작성해야 하는지 추론해야 한다. 해당 캡처는 dialog 배경이므로 일반 폼 전체의 도움말 유무까지 단정하지 않는다. 단계별/전체 범위의 명칭과 묶음은 보완 대상이다.

**개선 방향:** 단계 안의 기대 결과와 테스트 전체의 공통 기대 결과를 제목·묶음에서 구별하고 공통 필드가 선택적이면 이를 드러낸다. 입력 필드 자체를 제거하지 않는다.

**검증:** '각 단계의 검증 기준'과 '마지막 전체 검증 기준'을 따로 제시해 올바른 위치에 작성하는지 확인한다. Text↔Steps 전환 후에도 의미를 유지해야 한다. 다음 live 검토에서는 dialog 없는 폼의 스크롤 구간을 추가 확인한다.

## UX-R17 — Cases와 Run에서 섹션 구조를 다시 해석해야 함 · P1

**화면:** [Cases 전체](./ux-evidence/e2e-0921-scope-all.png)는 Commerce / Login / Recovery 경로를 평면으로 표시한다. [Run](./ux-evidence/e2e-0921-run-1280.png)은 COMMERCE, LOGIN, RECOVERY를 같은 깊이의 그룹 제목으로 표시한다. 왼쪽 트리만 계층을 나타낸다.

**직관성 문제:** 작성할 때 익힌 소속 표현이 실행에서 바뀐다. Recovery가 Login 하위라는 사실이 목록 본문에서 사라지고, 동명 Login은 전체 경로도 표시되지 않는 그룹 제목만으로 식별하기 어렵다. 이번 캡처에는 두 Login 그룹이 동시에 보이지 않으므로 동명 그룹의 전체 스크롤 검증은 남아 있다.

**개선 방향:** Cases와 Run에서 같은 섹션 계층을 같은 시각적 문법으로 표현한다. 들여쓰기·그룹 소속·동명 구분을 공통 기준으로 삼고, 상태별 그룹 등 계층이 아닌 모드에는 트리 깊이를 억지로 적용하지 않는다.

**검증:** 같은 fixture의 Cases→Run 전환에서 Commerce/Login/Recovery와 Account/Login을 다시 탐색하지 않고 구별한다. UX-R10을 Cases 한 화면의 수정으로 끝내지 않는다.

## 기존 판단에서 추가로 바로잡을 부분

- **UX-R05, 이동과 기록의 명칭:** [Run toolbar](./ux-evidence/e2e-0921-run-1280.png)의 Pass & Next는 저장+이동인데 바로 옆 Failed → / Blocked → / Untested →는 상태별 이동이다. 같은 줄의 비슷한 형식이 다른 결과를 만든다. 상태별 이동은 '다음 미실행'처럼 목적이 드러나야 하며 잘못된 결과 기록 위험 때문에 우선순위를 P1로 높인다. 실제 오기록이 발생했다고 주장하지 않는다.
- **UX-R04, 모바일까지:** [모바일 목록](./ux-evidence/e2e-0921-mobile-list.png)은 첫 TC가 화면 하단에서 시작하고 [모바일 상세](./ux-evidence/e2e-0921-run-390.png)도 헤더·통계가 상단을 상당 부분 차지한다. Back to tests가 있다고 모바일 전체가 직관적인 것은 아니다. 상세 대체 방식은 보존하되 읽기 공간을 별도로 개선해야 한다.
- **UX-R03, 대상 식별:** [Cases 패널](./ux-evidence/e2e-0921-case-panel-1280.png)에서 제목은 `C6 Ten-step c...`로 잘리는 반면 보조 메타는 길게 펼쳐진다. 지침 순서뿐 아니라 현재 연 케이스를 확인할 정보의 우선순위도 문제다.
- **좋은 대조 사례:** [폐기 확인](./ux-evidence/e2e-0921-cancel-dialog.png)의 Keep editing / Discard changes는 결과를 예상할 수 있다. [My Tests](./ux-evidence/e2e-0921-my-tests-assigned.png)는 대상 case·Run·상태·Open test가 같은 행에 있다. 이런 명확함을 다른 화면의 완료 기준으로 삼는다.
