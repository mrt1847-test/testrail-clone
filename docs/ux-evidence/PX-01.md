# PX-01 — Cases 계층·조회 범위·추가 대상

완료: 2026-09-25. 실제 로컬 main에서 구현했다. 기준 코드 d54e450 → 구현 1eecf2b. [활성 계획](../superpowers/plans/2026-09-23-testrail-page-ux.md)의 PX-01 수용 기록이다.

## 변경과 공식 비교

[공식 Sections 화면](https://support.testrail.com/hc/article_attachments/39004473715092)을 기준으로 트리→섹션 제목→소속 케이스→섹션 끝 추가의 흐름을 비교했다. 원본은 제공된 이미지이므로 같은 제품 버전·viewport의 픽셀 비교라고 주장하지 않는다.

기존 화면은 본문 그룹을 같은 깊이의 전체 경로로 나열하고, 직접 케이스가 없는 Commerce/Account 부모를 생략했다. all에서도 General 같은 선택 경로가 본문 범위와 검색 도구 앞에 반복됐다.

- 본문에 조회 결과의 조상만 보충하고 트리 순서로 정렬한다. 추가한 부모에는 케이스를 복제하지 않는다. 표시 루트 기준 깊이로 제목·행·Add Case를 함께 들여쓴다. 전체 경로는 접근성 이름과 tooltip에 보존한다.
- 들여쓰기는 단계당 16px, 80px 또는 화면 폭 6% 중 작은 값이다. 세 단계 fixture는 1440/1280에서 0·16·32px, 390에서 0·16·23.4px였다.
- all 제목은 All sections와 실제 건수만 표시한다. 트리는 추가 위치를 점선으로 표시하고 aria-current=location을 사용한다. direct/subtree의 조회 선택 강조와 구별한다. 키보드 포커스 테두리는 별도로 유지한다.
- 그룹 건수는 직접 소속 건수다. 접기 이름도 direct cases in 경로로 표시하고 해당 그룹만 접는다. 직접 케이스가 없는 조상에는 접기 버튼이 보이지 않으며 빠른 추가는 유지된다. 하위 트리 전체를 접는 탐색 트리 동작과 구별한다.
- 상단 Add Test Case는 전체 작성, 그룹 끝 Add Case는 제목만 빠르게 저장하는 기존 UI-069를 재사용했다. ProjectContentHeader에 중복 구현은 추가하지 않았다.

## 전체 페이지 증거

동일한 5개 활성 케이스 fixture로 before/after를 비교했다. 폭별 full-page 캡처이므로 이미지 높이는 viewport보다 길 수 있다. 변경 전 all의 추가 위치는 General, 변경 후는 Commerce이며 조회 결과 C1~C5는 같다.

1280 all의 최초 before는 viewport 전환 도중 잘못 렌더링된 캡처여서 제외했다. 전체 페이지 비교의 세 폭 근거는 정상적인 subtree 쌍이다. 최종 after 6장은 각각 열어 검토했다.

판정: 넓은 화면은 기존 약 260px 탐색 열을 유지하고 본문이 주 작업 폭을 차지한다. 부모 배경/그룹 경계와 상대 들여쓰기로 동명 Login의 소속을 구별한다. 제목 행과 추가 행동이 같은 그룹 폭을 사용하고, 선택·메타 열을 읽을 수 있다. 390에서는 탐색 뒤 본문을 세로로 배치하며 제목은 줄바꿈되고 기존 반응형 메타 숨김을 유지한다. 범위는 검색보다 위에 한 번 나타나고 전체 작성은 상단에 한 번 존재한다. 0건 부모 표시로 세로 길이는 늘지만 케이스의 소속과 추가 대상이 명확해지는 비용으로 수용했다. 세 폭 모두 수평 overflow는 없었다. 독립 사용자 수용 결과는 아니다.

## 동작과 실제 키보드 검증

전용 메모리 API localhost:4108 + 로컬 Vite localhost:5188에서 확인했다. 사용자 DB를 초기화하지 않았다. 프로젝트 1, Suite 1, General=1, Commerce=2, Login=3, Recovery=4, Account=5, Account/Login=6. C1/C2는 3, C3/C4는 4, C5는 6 소속이다. 빌드에 의한 메모리 서버 재시작 뒤에는 같은 fixture를 복원했다.

| 검증 | 관찰 결과 |
| --- | --- |
| Commerce direct | 0건, 빈 상태와 Commerce 빠른 추가 표시 |
| Login direct / subtree | C1/C2 2건 / C1~C4 4건. subtree 표시 깊이는 Login=0, Recovery=1 |
| Commerce subtree / all | C1~C4 4건 / C1~C5 5건. 빈 조상은 표시하되 케이스 중복 없음 |
| all에서 트리 위치 이동 | 조회 5건 유지, 전체 작성/빠른 추가 위치만 변경 |
| Search administrator | C5 1건, Account→Login 조상 문맥 유지 |
| Compact rows | 메뉴 선택 상태 확인, Login/Recovery 4건과 메타·그룹 제목 유지 |
| 실제 ArrowDown / ArrowUp | Commerce→Login / Login→Commerce로 포커스·조회 이동 |
| 실제 Space / Enter | C3 선택 후 Recovery 접기. 1 selected · 2 direct cases 표시, 다시 펼치면 선택 유지 |
| 실제 빠른 추가 Enter | Recovery의 제목 입력으로 C6 생성. API GET /api/cases/6에서 sectionId=4, 제목 Verify recovery token expiry 확인 |
| 빠른 추가 Escape | 추가 입력 종료, 저장한 C6 미리보기 유지. 검증 후 복원 가능한 삭제 보기로 이동하여 활성 fixture 5건으로 복귀 |
| 전체 작성 Enter / Tab | 상단 링크로 전체 폼 진입, Recovery 선택. 제목에서 Tab으로 case-section에 포커스 이동 |
| 전체 작성 Cancel Enter | 빈 폼 취소 후 같은 suite/section 목록 복귀, 새 케이스 생성 없음 |

## 코드 검토와 자동 검증

독립 읽기 전용 검토에서 정상 트리의 확정 Critical/Important 문제는 없었다. 지적된 두 경미한 사항은 같은 작업에서 보완했다. 빈 부모 접기 혼동은 위 표시로 정리했다. 부모 메타데이터가 없는 섹션의 케이스 누락은 테스트 실패([1]만 반환)로 재현한 뒤 렌더링되지 않은 원본 그룹을 보존하여 [1,2] 반환으로 수정했다.

- 최초 계층·범위 테스트: 4 fail → 수정 후 관련 11 pass.
- 검토 회귀: 부모/섹션 메타데이터 누락 테스트 1 fail → 관련 10 pass.
- 최종 `npm.cmd exec -- vitest run apps/web/src --maxWorkers=2 --minWorkers=1`: 85 files, 328 tests pass.
- 최종 `npm.cmd run lint -w apps/web`: exit 0.
- 최종 `npm.cmd run build -w apps/web`: exit 0. 기존 큰 JS 청크 경고는 남아 있다.

## 문서 영향과 범위

PRODUCT_SPEC의 UI/UX 보존 계약에 Cases의 상대 계층·조회/추가 위치·직접 접기 의미를 동기화했다. FEATURE_CHECKLIST의 기존 Case CRUD 항목에 PX-01 증거를 연결했다. 실행 원장의 PX-01 체크와 NEXT_ACTIONS Current를 갱신했다. API_SPEC/DATABASE_SCHEMA/DOMAIN_MODEL/ARCHITECTURE는 계약·저장 구조·소유권 변경이 없어 수정하지 않았다. ROADMAP의 방향은 동일하다.

Ruling: 사용자의 로컬 파일 작업 지시에 따라 실제 로컬 main을 사용했다. 별도 worktree 구현이나 중복 실행 원장을 만들지 않았다. 브라우저 캡처의 임시 파일만 작업 환경에 저장한 뒤 검증된 파일을 로컬 docs로 옮겼다.

PX-01만 완료했다. PX-02 이후와 UI-021의 외부 첨부 bytes(E01)·지정 테스터 독립 수용(E03)은 이 결과로 완료 처리하지 않는다.
