# Run 상태 통계의 상단 배치

작성일: 2026-09-19
상태: UI-040의 설계 계약. 완료 여부는 상위 문서의 체크박스·증거, 현재 실행 순서는 NEXT_ACTIONS만 따른다. 아래 문제 설명은 최초 설계 시점의 근거다.

상위 기준: [UI/UX 기본방침](./USABILITY_REALIGNMENT_2026-09-18.md). 완료 추적: 같은 문서의 **UI-040**. 관련 설계: [읽기 중심 패널과 공통 결과 입력창](./RUN_RESULT_DIALOG_DESIGN_2026-09-19.md).

## 1. 목적과 참고 이미지

현재 왼쪽 상태 통계 영역은 기본 펼침 상태에서 약 208px(`lg:w-52`)을 차지한다. 섹션 트리까지 열면 통계 / 트리 / 목록 / 케이스 상세의 네 열이 되어, 테스트 제목과 수행 지침을 읽는 공간이 좁아진다.

사용자가 첨부한 `codex-clipboard-79aba3d5-5c46-4783-9317-bfcdd2b5537e.png`처럼 **Run 제목 아래, 테스트 목록 위에 차트·상태별 건수·통과율을 배치**한다. 왼쪽 통계 열은 접어 두는 것이 아니라 작업 영역에서 제거한다. 확보한 폭은 목록과 케이스 상세에 돌려준다.

이미지는 배치 방향의 참고이며 현재 제품 검증 증거가 아니다. 큰 카드 두 개, 여백, 색상이나 오른쪽 전체 메뉴를 그대로 복제하지 않는다. 섹션 트리의 좌우 위치는 이번 작업에서 바꾸지 않는다.

## 2. 목표 화면 구조

```text
Run 제목 · 실행 상태                              Run utilities
작은 도넛 차트  |  상태별 이름·건수·비율  |  통과율 · 미실행/전체
─────────────────────────────────────────────────────────────
섹션 트리(선택) | 검색·필터 / 테스트 목록 | 케이스 지침·상세(선택)
```

- 상단은 하나의 낮은 요약 영역으로 구성한다. 중첩 카드나 상태별 큰 타일은 추가하지 않는다.
- 차트는 데스크톱 약 96–112px의 기존 도넛 차트를 우선 재사용한다. 상태명·건수·비율은 차트 옆의 간결한 범례로 표시한다.
- 핵심 수치는 `73% passed`와 `9 / 59 untested`처럼 의미가 분명한 문구로 표시한다. 같은 통과율을 차트 중앙과 별도 대형 카드에 중복 강조하지 않는다.
- 이름이 긴 Run이나 좁은 화면에서도 제목, 상태 요약, 목록 순서를 유지한다. 통계 전체를 sticky로 고정해 목록의 세로 공간을 계속 점유하지 않는다.
- 사이드바 열을 제거한 만큼 workbench grid와 높이 계산을 함께 조정한다. 기존 `calc(100dvh - ...)` 상수를 그대로 두어 표나 상세 하단이 잘리지 않게 한다.

## 3. 숫자의 의미와 데이터 계약

요약 제목/접근성 설명에 **Run 전체 통계**임을 명시한다. 통계의 분모는 현재 페이지·선택 행·선택 섹션·검색 결과가 아니라 해당 Run 전체 테스트 수다.

| 표시 | 기준 |
| --- | --- |
| 전체 테스트 | Passed + Failed + Blocked + Retest + Untested |
| 통과율 | Passed / 전체 × 100. `complete`와 혼용하지 않는다. |
| 상태별 비율 | 해당 상태 / 전체 × 100 |
| 미실행 | Untested 건수 / 전체 건수 |
| 결과 기록 비율(표시할 경우) | (전체 − Untested) / 전체. 최종 성공이나 작업 완료를 뜻하지 않으므로 통과율과 구분한다. 기본 화면의 추가 대형 지표로 만들지 않는다. |

- 기존 Run detail counts와 `runProgressSegments`의 계산을 재사용한다. 프런트에서 현재 조회된 행만 세어 전체 통계로 표시하지 않는다.
- 숫자는 정수 건수와 반올림한 정수 비율을 사용한다. 차트 면적은 실제 건수 비율로 계산한다. 반올림으로 상태별 표시 비율 합이 99/101이 되는 경우 건수를 조작하지 않는다.
- 표준 검증값: Passed 43 / Blocked 2 / Retest 3 / Failed 2 / Untested 9 → 전체 59, 통과율 73%, 미실행 9/59(15%). 결과 기록 비율은 85%이며 73%와 다른 값이다.
- 전체 0건은 `0 tests`와 중립적인 빈 차트로 표시한다. NaN/Infinity나 임의의 100%를 표시하지 않는다.
- 로딩은 로딩 상태로, 요청 실패는 오류·재시도로 구분한다. 미수신 데이터를 실제 0건처럼 보이지 않게 한다.
- 결과 저장·bulk 저장·정정·구성 변경 후 기존 query 갱신 계약으로 표/통계/상세 상태가 일치해야 한다. 저장 실패나 롤백에서 성공 통계가 남지 않아야 한다. UI-030–032의 대상·부분 실패 의미를 유지한다.

## 4. 필터와 기존 기능의 이동

### 상태 통계는 조회 동작

- 범례의 상태명·건수를 클릭하면 기존 상태 필터를 적용한다. 상태 변경이나 결과 생성 요청은 발생하지 않는다.
- 선택된 필터를 색상뿐 아니라 텍스트/선택 표시와 접근성 상태로 알린다. 0건 상태도 이름·0을 유지하고, 선택하면 해당 범위에 결과가 없음을 표시한다.
- `All statuses`는 상태 필터만 해제한다. 검색어·섹션 등 다른 필터를 몰래 초기화하지 않는다.
- 전체 Run 통계는 필터링해도 동일한 분모를 유지한다. 목록에는 현재 조건의 결과 건수와 활성 필터를 별도로 표시한다. 전체 Failed가 2건이어도 선택 섹션에 0건일 수 있음을 설명할 수 있어야 한다.
- 필터 변경 시 페이지·선택 행·상세와 URL을 기존 계약에 맞게 동기화한다. 사라진 테스트를 다음 결과 입력 대상으로 조용히 유지하지 않는다. bulk 선택 범위도 UI-032 규칙을 지킨다.
- 차트 조각의 마우스 클릭은 보조 수단이다. 동일 필터를 키보드로 조작할 수 있는 범례 버튼을 반드시 제공한다.

### 왼쪽 사이드바의 다른 역할을 유실하지 않는다

| 기존 요소 | 이동 후 |
| --- | --- |
| Status 건수·필터 | 상단 요약과 범례 |
| Progress 탭의 차트·요약 | 상단으로 통합. 동일 내용의 별도 Progress 패널을 다시 만들지 않음 |
| Activity | Run utilities의 명확한 Activity 진입점 → 기존 내용의 보조 drawer/dialog. 닫기·포커스 복귀 제공 |
| Run Defects | Run utilities의 결함 요약 링크 유지. 테스트별 Defects는 케이스 상세에 유지 |
| Pass & Next / 이전·다음 테스트 | 목록 또는 선택 테스트 가까운 짧은 실행 작업 줄. 통계 범례에 섞지 않음 |
| 다음 Failed/Blocked/Untested, 단축키, Jump to next 설정 | 같은 실행 작업 줄의 보조 메뉴/설정. 기존 실행 의미 보존 |

UI-037–039가 먼저 구현됐으면 그 패널 작업 줄을 재사용한다. 아직 구현되지 않았으면 기존 `RunExecutionToolbar`를 적절한 작업 위치로 옮길 뿐, 이 작업에서 결과 모달을 함께 구현하지 않는다. 어느 순서든 동일 버튼을 여러 위치에 복제하지 않는다.

기존 사이드바 mode/collapse 저장값은 더 이상 왼쪽 통계 열을 복원하지 않아야 한다. 관련 없는 사용자 설정을 초기화하지 않는다.

## 5. 반응형·접근성 기준

- 1440×1000과 1280×720에서는 요약을 수평 배치한다. 기본 길이 라벨의 요약 영역 높이는 약 140px 이내를 목표로 하되, 텍스트 확대·긴 라벨은 잘리지 않고 줄바꿈하도록 한다.
- 1280×720, 섹션 트리와 상세패널을 연 같은 조건에서 기존 통계 열의 208px을 점유하던 grid track이 없어야 한다. 동일 폭 설정으로 목록/상세의 실제 폭 전후를 측정한다. 단순히 통계를 옮기고 빈 열을 남겨서는 안 된다.
- 390×844에서는 작은 차트와 핵심 요약, 두 열 범례 등으로 줄바꿈한다. 상태 목록을 세로로 길게 쌓아 예전 사이드바를 화면 위에 그대로 붙이지 않는다. 페이지 가로 넘침 없이 초기 viewport에 목록 제목과 첫 테스트 행이 보여야 한다(기본 fixture, 상세 닫힘).
- UI-033의 1280px에서 최소 6개 완전한 행과 제목/상태 가독성 기준을 회귀 검증한다. 지표 공간 확보를 위해 케이스 지침을 숨기거나 글자를 과도하게 줄이지 않는다. 충족하지 못하면 완료 처리하지 않고 충돌 근거를 기록한다.
- 상태는 기존 공통 상태 색상과 텍스트를 사용한다. 차트만으로 의미를 전달하지 않는다. 범례 버튼에 상태·건수·선택 여부를 제공하고 Tab/Enter/Space로 사용할 수 있게 한다.
- 집계 갱신은 필요한 짧은 문구로 전달한다. 차트 전체가 매번 과도하게 다시 낭독되거나 필터 후 포커스가 유실되지 않게 한다.

## 6. 구현 경계와 재사용

시작 파일은 모두 `apps/web/src/features/runs/` 아래다.

- `components/RunDetailPage.tsx`: 헤더 아래 요약 위치, workbench grid에서 sidebar 열 제거, 필터/실행 작업 연결.
- `components/RunDetailSidebar.tsx`, `RunStatusSidebar.tsx`: Run 화면의 상시 소비를 제거하고 기존 기능 이동. 다른 소비처를 확인한 뒤 필요 없는 코드만 정리.
- `components/RunProgressChart.tsx`, `RunSummaryBar.tsx`, `RunProgressPanel.tsx`: 기존 차트/범례/수치 표현을 조합·정리. 서로의 범례나 수치를 중복 표시하지 않음.
- `components/RunExecutionHeader.tsx`, `RunExecutionToolbar.tsx`: 기존 보조 메뉴와 실행 동작의 새 위치 연결.
- `utils/runProgressSegments.ts`, `runProgressChartGeometry.ts`: 계산·색상·차트 기하 재사용 및 회귀 테스트.

필요하면 `RunStatusOverview`라는 작은 조합 컴포넌트를 추가한다. 새로운 차트 라이브러리, 상태 집계 API, 저장 동작, 전역 프로젝트 헤더 재설계는 범위 밖이다. 섹션 트리 자체를 제거하거나 위치를 반전하지 않는다.

## 7. UI-040 — 하나의 작업 단위

- [ ] 동일 fixture로 1280×720/390×844의 변경 전 통계·목록·상세 폭과 첫 행 위치를 기록한다.
- [ ] 헤더 아래 요약을 구성하고 전체 통계 계산·빈/로딩/오류 상태를 연결한다.
- [ ] 왼쪽 통계 grid track을 제거하고 남은 영역의 폭·높이 계산을 조정한다.
- [ ] 상태 필터, Activity/Defects, 실행·이동·단축키의 접근 경로를 보존하고 중복 노출을 제거한다.
- [ ] Run 전체 통계와 목록 필터의 범위를 검증한다. 상태 클릭만으로 결과 mutation이 발생하지 않는지 확인한다.
- [ ] 단건/bulk 결과 저장, 실패/롤백, 조회 조건 변경 후 수치·행·상세·URL 일치를 확인한다.
- [ ] 관련 테스트, 웹 타입 검사·빌드, 키보드와 세 viewport 화면 검증을 수행한다.
- [ ] `docs/ux-evidence/UI-040.md`에 전후 측정·실행 결과·캡처를 남기고 모든 조건 통과 후에만 원본 UI-040을 완료 처리한다.

검증 fixture는 59건의 위 상태 분포, 두 개 이상의 섹션, 사전조건·스텝·기대 결과가 있는 케이스를 포함한다. 별도로 전체 0건, 전부 Untested, 전부 Passed, 조회 실패를 확인한다. 성공 결과 기록 후 분포가 실제로 바뀌는지도 확인한다.

필수 캡처는 1440×1000, 1280×720, 390×844의 초기 화면, 상태 필터 적용 화면, 케이스 지침을 연 상세 화면이다. 같은 데이터/화면 조건으로 전후를 비교하고, 최종 응답에 핵심 전후 이미지를 첨부한다. 참고 이미지나 과거 캡처로 이번 결과를 대신하지 않는다.

## 8. 실행 순서

실행 순서는 NEXT_ACTIONS만 따른다. 이 문서는 진행 위치를 복제하지 않는다. UI-040의 단위 검증은 해당 시점의 패널을 기준으로 상단 통계·필터·폭을 검증하며, UI-037–039의 최종 결과창/지침 배치를 먼저 구현하도록 요구하지 않는다. UI-021 최종 통합 검증에서 상단 통계와 실제 테스트 수행 흐름을 함께 확인한다. 현재 정책·시안 검토·검증 단계는 상위 문서 §5와 §8을 따른다.
