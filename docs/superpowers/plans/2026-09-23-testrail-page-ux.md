# TestRail 페이지 구성 개선 실행 계획

> **For agentic workers:** 구현 시 superpowers:executing-plans를 사용해 한 번에 한 단위씩 수행한다. 아래 체크는 구현 및 검증 완료에만 사용한다.

**Goal:** TestRail 공식 화면을 기준으로 Cases·작성·Run·결과창을 일관된 탐색→읽기→작성/기록 공간으로 개선한다.

**Architecture:** 기능별 패치를 늘리는 대신 페이지별 영역 관계와 정보 위계를 함께 수정한다. 기존 React 상태·조회·저장 계약은 유지하고 표현 및 배치만 해당 페이지 책임 아래 정리한다.

**Tech Stack:** React 18, TypeScript, Tailwind, Vite, 기존 서버 테스트 도구.

**Spec (필요할 때만 해당 페이지 확인; 전체 읽기 금지):** [공식 화면과 페이지 전체 비교](../../TESTRAIL_PAGE_COMPOSITION_REVIEW_2026-09-23.md). 세부 근거는 [직관성 기록](../../UI_INTUITIVENESS_REVIEW_2026-09-22.md), [E2E 검토](../../E2E_USABILITY_REVIEW_2026-09-21.md).

이 문서는 **새 개선 작업의 범위·체크 원장**이다. 실행 순서는 [NEXT_ACTIONS](../../NEXT_ACTIONS.md)만 관리한다. 검토 문서에 새 구현 체크를 덧붙이지 않는다. 등록일 2026-09-23, 구현 완료 항목 없음.

## 최소 입력 규칙

- 기본 읽기: NEXT_ACTIONS + 아래 공통 제약 + **현재 PX-ID 절 하나**. 이미 문맥에 있는 공통 제약은 다시 읽지 않는다.
- 각 PX 절은 변경 파일·계약·행동·완료 기준을 포함한다. 다른 작업의 전체 내용이나 검토 보고서를 선행 필독으로 삼지 않는다. 선행 작업은 완료 여부와 필요한 인터페이스/증거 요약만 확인한다.
- 공식 비교는 현재 페이지의 참조만 연다. 아래 직접 링크를 사용하고 전체 보고서를 순회하지 않는다. 판단 충돌/근거 공백이 있을 때만 Spec의 해당 절을 추가 확인한다.
- 완료 체크는 이 원장에 유지하되 완료 절은 기본 읽기에서 제외한다. 상세 실행 이력은 각 ID 증거에만 기록한다. 새 작업을 넣어도 문서 전체를 다시 읽는 규칙을 만들지 않는다.
- PowerShell 부분 읽기 예시(헤더 목록은 `rg -n '^## ' <파일>`):

```powershell
$planText = Get-Content -Raw docs/superpowers/plans/2026-09-23-testrail-page-ux.md
[regex]::Match($planText, '(?ms)^## 공통 제약과 완료 방식.*?(?=^## |\z)').Value
[regex]::Match($planText, '(?ms)^## PX-01 —.*?(?=^## |\z)').Value
```

PX-01을 Current ID로 바꾼다. 파일을 읽더라도 도구 출력에는 필요한 절만 반환한다.

## 공통 제약과 완료 방식

- 기존 작업의 완료 상태를 추정하지 않는다. 2026-09-23 확인한 원본 큐는 UI-066 진행 중이다. 최신 포인터는 NEXT_ACTIONS를 따른다. 구현 전에 실제 대상 checkout과 진행 중 변경을 확인한다.
- 1440×1000 / 1280×720 / 390×844에서 같은 fixture의 전체 페이지 before/after를 남긴다. TestRail 원본 참조를 함께 연결한다. 개별 컴포넌트 crop만으로 합격하지 않는다.
- 페이지 목적, 탐색/본문/보조 영역의 비율, 정보 위계, 행동 대상, 시선 흐름, 페이지 간 일관성을 각각 판정한다. 버튼 존재·overflow 0·빌드 성공만으로 완료하지 않는다.
- 일반 결과 저장은 현재 테스트 유지, 명시적 다음만 이동한다. 목록 Status와 상세 Add Result의 공통 입력창을 유지한다. 영구 왼쪽 통계 열을 다시 만들지 않는다.
- 원본 사용자 데이터 초기화·새 저장소 생성·권한 변경·예약 변경은 범위 밖이다. 실제 quota/rate limit 감지 시 즉시 저장소 변경을 중단한다.
- 제품 변경 단위마다 `npm.cmd run lint -w apps/web`, `npm.cmd run build -w apps/web`를 실행한다. 동작 변경에는 관련 회귀 테스트를 추가하고 프로젝트의 기존 실행 방법으로 실행한다. 순수 간격/색 조정에 구현을 그대로 베낀 단위 테스트를 만들지 않는다.
- 증거는 `docs/ux-evidence/PX-01.md` 등 각 ID 파일에 기록한다. 각 체크 완료에는 구현 diff, 명령/결과, 전체 화면, 실제 키보드 조작, 미검증 범위가 필요하다. 독립 사용자 수용은 UI-021/E03에서 별도 판단한다.

## 검토 시 놓치기 쉬운 조건

1. 직접 TC 없는 부모·동명 형제·3단계 이상 계층: PX-01에서 소속과 범위를 검증한다.
2. 긴 제목·10-step·좁은 화면: PX-02/03에서 지침 가독성과 공간 배분을 검증한다.
3. 열린 1개와 체크한 여러 개가 다른 상태: PX-03에서 결과/할당 대상을 검증한다.
4. 저장된 결과와 실패 첨부가 공존하는 상태: PX-04에서 남은 행동과 종료 의미를 검증한다.
5. 비어 있는 요약과 다수 Run/구성: PX-05에서 공식 동일 상태 근거 없이 과잉 재설계하지 않는다.

## PX-01 — Cases를 하나의 계층 탐색·작업 공간으로 구성

**현재 작업 공식 참조:** https://support.testrail.com/hc/article_attachments/39004473715092

**파일:** `apps/web/src/features/cases/components/CaseListPane.tsx`, `TestCaseWorkspace.tsx`(같은 디렉터리), `apps/web/src/features/cases/utils/caseRepositoryGrouping.ts`, `apps/web/src/features/projects/content-header/ProjectContentHeader.tsx`. 동작 회귀는 기존 `caseRepositoryGrouping.test.ts`를 확장한다.

**입출력 계약:** 기존 sectionId/parentSectionId·그룹 depth와 direct/subtree/all을 소비한다. API나 TC 소속은 변경하지 않고 제목·트리 강조·본문 그룹·빠른 추가가 같은 범위를 표현하게 한다.

- [ ] 공식 Sections 이미지와 현재 all/subtree 전체 화면을 확보한다. Commerce/Login/Recovery, Account/Login, 직접 TC 없는 부모를 포함한다.
- [ ] 부모/자식 제목·소속 TC·빠른 추가를 일관된 들여쓰기와 그룹 경계로 묶는다. 표시 범위의 최상위 깊이를 기준으로 하며 좁은 폭에서는 들여쓰기 상한을 적용한다. 선택/메타 열과 제목 읽기 폭을 함께 확인한다.
- [ ] 본문 제목은 실제 조회 범위를 나타내게 한다. all의 트리 포커스는 특정 섹션만 조회하는 강조와 구별하고, 경로/검색 제목의 중복을 줄인다.
- [ ] 상단 Add Test Case는 전체 작성, 섹션 끝 Add Case는 빠른 제목 추가로 정리한다. 같은 전체 작성 메뉴 중복을 제거한다.
- [ ] direct/subtree/all별 소속 TC 수·중복 없음, 접기/숨겨진 선택, 검색/Compact, 실키 탐색을 검증한다. 전체 페이지에서 계층과 행동 대상을 설명 없이 구별할 수 있는지 판정하고 증거를 남긴다.

**완료:** 트리에서 본 계층이 본문에 이어지고 현재 범위·추가 대상이 일치한다. **제외:** 결과 저장·권한·이동 정책 변경.

## PX-02 — 작성·읽기·편집을 연속된 내용 중심 페이지로 구성

**현재 작업 공식 참조:** https://support.testrail.com/hc/article_attachments/35637920570644

**파일:** `apps/web/src/features/cases/components/`의 `AddCasePage.tsx`, `CaseAuthoringForm.tsx`, `ExpandableCaseDetail.tsx`, `CaseDetailSidePanel.tsx`, `TestCaseWorkspace.tsx`.

**계약:** PX-01의 진입점/목적지를 유지한다. UI-066 초안 보호, UI-067/068 저장 경계를 재사용하며 폼 상태나 저장 payload를 재작성하지 않는다.

- [ ] 공식 작성 폼과 현재 전체 작성/읽기/편집을 같은 비교표에 놓는다. Text·3-step·10-step·긴 제목을 준비한다.
- [ ] 큰 별도 제목/Suite 카드와 폼 경계를 단순화하고 분류 필드를 짧은 메타 묶음으로 조직한다. 지침 입력이 이어지는 주 영역이 되게 한다. 메타를 무조건 아래로 보내지 않는다.
- [ ] 읽기 패널의 제목/메타/사전조건 중복을 제거하고 제목→한 번의 요약→지침으로 정리한다. 버전/빈 첨부가 지침보다 강조되지 않게 한다. 단계별 Expected와 공통 Expected의 적용 범위를 명확히 표시한다.
- [ ] 좁은 패널의 2열 입력을 폭에 맞게 전환하고, 모바일은 활성 상세/편집을 보여준 뒤 목록으로 돌아오는 구조로 맞춘다.
- [ ] 저장/취소·초안 보호·마지막 step·고정 footer·실키/IME를 확인한다. UI-072가 소유하는 복귀 문맥과 충돌하지 않는지 검증한다. 세 폭 전체 화면을 남긴다.

**완료:** 작성 순서와 현재 대상이 페이지 전체에서 명확하고 지침이 주 작업 공간을 차지한다. **제외:** 새 템플릿·첨부 저장 인프라.

## PX-03 — Run의 읽기·실행 공간과 목록 제어를 함께 재배치

**현재 작업 공식 참조:** https://support.testrail.com/hc/article_attachments/35638122795924

**파일:** `apps/web/src/features/runs/components/RunDetailPage.tsx`, `RunStatusOverview.tsx`(같은 디렉터리). 세부 목록/패널의 실제 하위 컴포넌트는 이 페이지의 import를 따라 수정한다.

**계약:** 현재 선택 test와 bulk 선택 집합, scope·status filter는 별개의 상태로 유지한다. 표시만으로 각 대상이 구별되어야 한다. Cases에서 확정한 계층 문법을 Run의 Section 그룹에도 적용한다.

- [ ] 공식 Run 전체/3-pane과 현재 기본·단일 선택·일괄 선택 화면을 비교한다. header/summary/list/detail의 경계와 차지하는 공간을 표시한다.
- [ ] 반복 문맥/전폭 헤더의 점유를 줄이고 상세가 주 읽기 영역이 되도록 폭·시작 위치를 조정한다. 통계는 상단 계약을 유지하되 상세를 밀어내는 누적 구조를 해소한다.
- [ ] 목록 설정·상태별 이동은 목록 영역으로, 현재 테스트 기록/다음은 상세 영역으로 묶는다. 상태별 이동 이름은 기록 동작과 구별한다. 결과 없는 다음과 저장 후 다음을 혼동하지 않게 한다.
- [ ] 6개 선택/C5 열림 상태에서 결과·할당 대상을 행동 가까이 표시한다. Cases와 같은 부모/자식·동명 섹션 구분을 적용한다.
- [ ] 긴 제목/10-step·0건/여러 섹션·필터·일괄 선택·모바일을 검증한다. 실제 결과 저장 후 해당 Run/test만 바뀌는지 확인한다. 정상 저장 유지/명시적 다음 및 키보드 경로를 검증한다.

**완료:** 전체 상태→선택 대상→지침→기록의 시선 흐름이 명확하고 목록 도구가 지침을 압도하지 않는다. **제외:** 결과 API 재설계·영구 차트 사이드바·기능 삭제.

## PX-04 — 결과 입력창을 상태가 바뀌어도 일관된 기록 공간으로 유지

**현재 작업 공식 참조:** https://support.testrail.com/hc/article_attachments/15881055029652

**파일:** `apps/web/src/features/runs/components/ResultEntryDialog.tsx`, `ResultEntryPanel.tsx`(같은 디렉터리), 연결된 저장/첨부 callback 소유자 `RunDetailPage.tsx`.

**계약:** 넓은 주 입력/좁은 보조 입력/안정된 footer를 보존한다. 저장 완료 결과와 미완료 첨부 상태를 구분하며 Retry가 결과를 중복 생성하지 않는다.

- [ ] 공식 결과창과 정상/저장 실패/첨부 일부 실패 화면을 비교한다. 정책 설명이 주 입력을 가리는 지점을 확인한다.
- [ ] 반복 안내를 관련 문맥에 간결히 배치한다. 부분 성공이면 저장 완료를 명확히 하고 주 행동을 남은 첨부 재시도로 맞춘다. 파일별/전체 재시도 대상을 구분한다.
- [ ] 저장 이후 종료를 저장 전 Cancel과 구별하고, 미완료 첨부 폐기가 저장된 결과를 지우지 않는다는 의미를 표시한다.
- [ ] 전체 저장 실패→재시도, 결과 성공/파일 실패→파일만 재시도, 종료/재개, 두 진입점, Escape/포커스 복귀를 검증한다. 요청 및 결과 수로 중복 없음도 확인한다.

**완료:** 무엇이 저장됐고 무엇이 남았으며 닫으면 무엇이 유지되는지 화면만으로 이해할 수 있다. **제외:** 새 저장소·결과 정책 변경.

## PX-05 — 비교 근거가 부족한 페이지의 대응 상태 확보 및 수정 범위 확정

**현재 작업 공식 참조:** https://support.testrail.com/hc/en-us/articles/7076810203028-Introduction-to-TestRail

**파일:** 새 증거 `docs/ux-evidence/PX-05.md`. 조사 대상은 `apps/web/src/features/projects/components/PlanDetailPage.tsx`, `apps/web/src/features/runs/utils/runListHubModel.ts`와 해당 허브/Overview/Milestone 페이지다. 이 단위에서는 제품 코드를 수정하지 않는다.

- [ ] 공식 Plan 실행 상세·Overview·Milestone의 동일 상태 전체 화면을 확보한다. 작성 폼/차트 crop을 대응 전체 화면으로 사용하지 않는다. 확보 실패 시 정확한 근거 공백을 기록한다.
- [ ] 현재 구성 없음/다중 구성, 빈 요약/데이터 있는 요약, blocked-only/혼합 Run을 전체 화면으로 비교한다.
- [ ] 전역/페이지 문맥, 요약/실행 진입, 설정/실행 구별을 평가한다. UX-R07/14/15 중 유지·철회·수정할 항목과 근거를 기록한다.
- [ ] 근거가 확보된 개선만 이 새 계획에 후속 구현 ID로 추가하고 NEXT_ACTIONS의 PX-06 앞에 넣는다. 각 단위에 변경 파일·before/after 목표·제외 범위·수용 기준을 작성한다. UI-021이나 PX-06으로 구현을 떠넘기지 않는다.

**완료:** 검토 결과와 구체적 후속 수정 또는 수정 불필요 판정이 남는다. 대응 화면을 못 구하면 완료 처리하지 않고 재개 조건을 기록하되 다른 페이지 작업을 막지 않는다.

## PX-06 — 페이지 간 조화와 직관성 통합 판정

**파일:** 새 증거 `docs/ux-evidence/PX-06.md`. 제품 수정 단위가 아니라 통합 수용 검증이다.

- [ ] Cases→전체 작성→목록 복귀→읽기→Run→결과→재개를 동일 fixture로 실조작한다. UI-071/072와 PX-05에서 추가된 구현의 완료 여부도 확인한다.
- [ ] 세 폭에서 페이지별 공식/before/after를 모으고 탐색·작업·보조 영역의 역할과 주 행동 표현이 이어지는지 비교한다.
- [ ] 경로를 읽어야만 아는 관계, 화면 밖 활성 상세, 일괄/단일 대상 혼동, 이동/저장 혼동이 남는지 실제 키보드와 함께 검증한다.
- [ ] 발견 결함은 원인 페이지의 단위로 되돌리고 미완료를 유지한다. 기능 테스트와 전문가 화면 판정, 독립 테스터 관찰을 구분한다.
- [ ] 통합 증거를 UI-021에 연결한다. E01 실제 bytes와 E03 독립 수용은 추정으로 완료하지 않는다.

**완료:** 개별 수정이 합쳐진 전체 업무 흐름에서도 페이지 구성과 조작 의미가 일관된다. 독립 사용자 수용을 대신하는 합격 인증은 아니다.
