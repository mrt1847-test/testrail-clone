# 테스트 실행: 읽기 중심 사이드패널과 공통 결과 입력창

작성일: 2026-09-19
상태: UI-037–039의 기본 계약과 UI-051의 결과 입력창 재정렬 계약. 완료 여부는 상위 문서의 체크박스·증거, 현재 실행 순서는 NEXT_ACTIONS만 따른다. UI-037–039의 완료 이력은 UI-051의 시각적 완성도를 증명하지 않는다.

상위 방침: [UI/UX 기본방침 §1.1](./USABILITY_REALIGNMENT_2026-09-18.md#11-product-foundation--case-management-and-actual-test-execution). 완료 추적은 같은 문서의 UI-037–UI-039 및 UI-051을 사용한다. 아래 순서는 이 설계 내부의 의존 순서이며 [NEXT_ACTIONS](./NEXT_ACTIONS.md)의 Current batch를 바꾸지 않는다.

## 1. 사용자 의도와 범위

테스터가 케이스의 사전조건·스텝·기대 결과를 읽는 공간을 긴 결과 입력 폼이 차지하지 않게 한다. 사이드패널의 Add result와 Run 테스트 목록의 Status 드롭다운은 **동일한 공통 결과 입력 대화상자**를 연다. 입력·검증·첨부·저장·오류 복구 동작은 진입 위치와 무관하게 같아야 한다.

여기서 목록은 **현재 Run의 테스트 인스턴스 목록**이다. 결과는 `projectId + runId + testId`에 귀속된다. 동일 케이스가 다른 Run에 있으면 상태가 다를 수 있으므로, 케이스 원본 관리 화면에 모호한 전역 실행 상태를 추가하지 않는다.

사용자가 제공한 이미지에서 채택할 방향:

- 이미지 1 (`codex-clipboard-a768b9fd-7c19-4c36-9764-97818b27bb2e.png`): **UI-051의 직접적인 배치 기준**. 왼쪽 Status 드롭다운 → Comment → 작은 첨부 영역, 오른쪽 Assign To → Version → Elapsed → Defects, 하단 Add Result / Cancel의 작은 직사각형 창.
- 이미지 2 (`codex-clipboard-f3be6acb-daaa-4444-a339-640ec54f4dd7.png`): 상세패널의 읽기/이력 영역과 하단 Add Result / Pass & Next / Assign To 작업 줄 분리.
- 참고 이미지는 이 대화에 첨부된 디자인 참고이며 현재 제품 검증 증거가 아니다. 이미지 1의 필드 배치와 행동 계층은 따르되 옛 색상·광고·차트를 복제하지 않는다. 이미지 2의 내용 없는 케이스 상태도 목표로 삼지 않는다.

## 2. 최초 설계 시 구현과 변경 이유 — 이력

- `RunDetailPage`의 사이드패널에는 `RunCaseContextPanel`, 담당자, `RunQPanePanel`, Results 탭의 `ResultEntryPanel`이 함께 있다. 입력 필드가 많아질수록 케이스 내용과 결과 입력이 긴 단일 패널에서 경쟁한다.
- `TestInstanceTable`에는 Status 열이 이미 있다. 현재 Passed는 즉시 저장하고, Failed/Blocked/Retest는 composer를 여는 분기가 있다. **열을 중복 추가하는 것이 아니라 기존 열의 발견성과 행동을 통일한다.**
- `ResultEntryPanel`의 기존 검증·템플릿별 필드와 UI-030/031의 결과/첨부 복구 계약은 유지한다. 별도 폼이나 저장 API를 두 진입점에 각각 만들지 않는다.

## 3. 선택한 형태: 컴팩트한 중앙 모달

| 형태 | 판단 |
| --- | --- |
| 중앙 모달 대화상자 | 채택. comment·첨부·오류를 수용하고, 목록/패널 어느 쪽에서도 같은 위치·포커스 계약을 제공한다. |
| 행 옆 작은 팝오버 | 비채택. 긴 comment, 파일 목록, 작은 화면에서 잘리기 쉽고 메뉴와 입력 폼의 닫힘 규칙이 충돌한다. |
| 또 다른 사이드 drawer | 비채택. 케이스를 읽던 패널을 가리거나 같은 혼잡을 다시 만든다. |

UI-051 레이아웃 기준은 데스크톱 폭 약 640px, 최대 680px, 높이 최대 `calc(100dvh - 32px)`이다. 본문은 왼쪽 약 2/3, 오른쪽 약 1/3의 2열이며 열 사이에는 여백 또는 얇은 구분선 하나만 둔다. 기본 Text 결과(추가 필수 필드/첨부 없음)는 1280×720에서 모든 기본 필드와 하단 버튼을 스크롤 없이 볼 수 있게 한다. 긴 내용은 본문만 스크롤하고 제목/하단 작업은 유지한다. 600px 미만 viewport에서는 좌우 약 12px 여백의 한 열로 전환하며, 가상 키보드가 열려도 활성 필드와 저장 조작에 접근할 수 있어야 한다. 전면 페이지나 새 브라우저 창으로 이동하지 않는다.

외곽 경계 한 개와 절제된 그림자만 사용한다. 필드별 카드, 큰 상태 타일, 중첩 테두리를 만들지 않는다. 상태는 작은 라벨+선택 컨트롤로 표현한다.

## 4. 기본 화면과 입력창 구성

### 실행 사이드패널: 읽기가 먼저

1. 케이스 번호·제목·현재 실행 상태와 필요한 최소 문맥.
2. 사전조건 → 순서가 있는 스텝 → 각 기대 결과. 공통 기대 결과가 있다면 스텝 존재 여부와 무관하게 읽을 수 있게 한다.
3. 결과/댓글·이력·결함은 조회 중심 보조 영역. 상시 comment/actual/첨부 입력 폼은 제거한다.
4. 짧은 하단 작업 줄: 주 동작 **Add result**, 보조 **Pass & Next**, 작은 담당자 변경 진입점. 기존 다른 위치의 동일 작업을 중복 노출하지 않는다.

UI-039의 구체적인 화면 계약은 상위 작업 본문을 따른다. 제목 다음에는 Type/Priority 등 짧은 읽기 전용 요약만 두고, Preconditions와 Action/Expected 쌍 또는 Text 지침을 실제 본문으로 배치한다. 결과 조회는 본문 아래 보조 영역이며 처음부터 입력 폼이나 결과 탭으로 지침을 대체하지 않는다. 체크박스 bulk 선택, 케이스 상세 열기, 저장 후 다음 이동은 서로 다른 동작이다. UI-044는 같은 지침의 케이스 읽기 화면, UI-049는 작성과 영속화 검증을 담당한다.

좁은 화면에서는 보조 동작을 작은 메뉴로 옮길 수 있다. 하단 작업 줄이 마지막 스텝을 가리지 않게 여백을 확보한다. 필수 수행 지침을 결과 입력 메뉴나 More fields 안으로 넣어서는 안 된다.

### 공통 결과 입력창

| 영역 | 내용 / 규칙 |
| --- | --- |
| 제목 | `Add result · C123 케이스 제목`, 긴 제목은 줄바꿈. Run 문맥과 저장 대상을 확인할 수 있어야 한다. 닫기 버튼에 접근성 이름 제공. |
| 왼쪽 주 입력 | Status는 라벨이 있는 단일 드롭다운(select/접근 가능한 combobox). 큰 색상 버튼·타일·라디오 격자는 금지. 그 아래 Comment(기본 3–4줄)와 한 줄 높이의 drop/browse 첨부 진입점. 파일이 생길 때만 파일별 상태/제거/재시도 목록을 표시한다. |
| 오른쪽 보조 입력 | Assign To → Version → Elapsed → Defects 순서의 작은 라벨+입력 컨트롤. 상태와 관계없이 같은 위치에 노출한다. Version/Elapsed/Defects를 More fields 뒤에 숨기지 않는다. 타이머 조작은 Elapsed 옆 작은 보조 제어이며 별도 카드가 아니다. |
| 상황별 입력 | Actual result는 왼쪽 Comment 아래 ‘추가 결과 정보’로 펼치되 해당 상태/프로젝트 정책상 필수이면 자동 노출한다. Defects는 오른쪽에만 한 번 표시한다. 상태 전환 시 초안 값을 삭제하지 않는다. |
| 템플릿별 추가 입력 | 선택적 custom fields, 스텝별/시나리오별 결과는 이름과 개수가 있는 펼침으로 접근한다. 프로젝트 필수 필드와 해당 템플릿의 필수 입력은 처음부터 노출하고 검증한다. 폼의 기본 2열 구조를 모든 기능의 상시 전시로 확장하지 않는다. |
| 수행 문맥 | 스텝별 결과를 펼치면 원래 스텝 설명·기대 결과를 함께 보여준다. 필요한 경우 같은 창 안의 읽기 전용 케이스 지침 펼침을 제공해 입력을 버리고 다른 페이지로 갈 필요가 없게 한다. |
| 하단 | 왼쪽에 주 버튼 **Add Result**와 텍스트형 **Cancel**. Save & Next는 Add Result 옆 작은 분할 메뉴의 명시적 보조 동작으로 보존하며 세 개의 큰 버튼을 나란히 놓지 않는다. 저장 중/부분 성공/오류는 이 영역 가까이에 표시한다. |

Comment의 템플릿 저장/미리보기/서식 도구는 필요할 때 여는 작은 보조 메뉴로 묶는다. 설명·정책 안내는 관련 필드의 짧은 도움말이나 해당 오류 상황에 배치하며 기본 화면 상단에 안내 배너를 쌓지 않는다. 필수 지침·검증 오류를 숨기는 것은 단순화가 아니다.

Assign To는 UI-051에서 결과와 함께 제출하는 **현재 Run 테스트 인스턴스의 담당자 초안**으로 추가한다. 기본값은 현재 담당자이며 선택 변경만으로 mutation을 보내지 않는다. 기존 권한·할당 API와 실제 선택 가능한 사용자를 재사용한다. 기존 API가 지원하는 내게 할당/해제 범위를 임의의 사용자 선택으로 위장하지 않는다. 결과 저장 성공 후 담당자 변경을 수행하며, 할당 실패 시 ‘결과 저장됨 / 담당자 변경 실패’를 구분하고 동일 testId의 할당만 재시도한다. 첨부와 할당 모두 성공하기 전 자동 닫기/다음 이동은 금지한다. 취소는 미저장 초안만 버리며 이미 저장된 결과를 취소했다고 표시하지 않는다. 일반 담당자 선택에 필요한 조회/권한 계약이 없다면 정확한 부족 항목을 blocker로 기록한다. 이 문서만으로 새 서버 API를 구현하거나 작동하지 않는 선택기를 완료 처리하지 않는다. 패널의 독립적인 담당자 변경 진입점은 유지한다.

```text
Add result · C123 케이스 제목                         ×
Status [Passed                  ▾] | Assign To [현재 담당자 ▾]
Comment                            | Version   [          ]
[                              ]   | Elapsed   [          ]
[                              ]   | Defects   [          ]
[파일을 놓거나 찾아보기]            |
──────────────────────────────────────────────────────
[Add Result ▾]  Cancel
```

위 배치는 기본 Text 결과 기준이다. 필수 스텝별 결과가 있는 템플릿은 필요한 영역이 늘어나도 허용하되 실제 지침과 검증을 보존한다. 모바일 읽기/Tab 순서는 Status → Comment → 첨부 → 보조 입력 → 필요한 추가 입력 → 저장이며 CSS 배치와 DOM 포커스 순서를 일치시킨다.

## 5. 진입점과 저장 의미

| 사용자 동작 | 창을 열 때 | 서버 변경 / 닫힌 뒤 |
| --- | --- | --- |
| 패널 Add result | 선택 테스트 대상으로 열기. 기존 프로젝트의 유효한 결과 상태 기본값을 사용하되 명확히 표시 | 열기만으로 저장하지 않는다. Save는 현재 테스트 유지. |
| 행 Status → Passed/Failed/Blocked/Retest 등 | 클릭한 행의 testId로 열기, 선택한 상태 미리 지정 | **Passed도 즉시 저장하지 않는다.** Cancel이면 현재 저장 상태 유지. |
| 같은 상태로 결과 추가 | Status 메뉴의 현재 상태를 다시 활성화하거나 Add result 사용 | 새로운 기록을 추가할 수 있어야 한다. 값이 바뀔 때만 발생하는 native select onChange에만 의존하지 않는다. |
| Add Result (기존 Save result) | 동일한 공통 검증/저장 수행 | 결과·선택한 첨부・담당자 변경 전체 성공 시 닫고 해당 테스트·목록·이력을 갱신. 다음 테스트로 이동하지 않는다. |
| Add Result 보조 메뉴 → Save & Next | 동일한 저장 + 명시적 다음 이동 의도 | 결과·선택한 첨부·담당자 변경 성공을 확인한 뒤 현재 필터/정렬에서 다음 대상으로 이동. 마지막이면 완료 피드백, 임의 순환 없음. |
| 기존 Pass & Next | 명시적인 빠른 성공 전용 예외로 유지 | UI-010의 원클릭 성공 후 이동 계약을 보존한다. 일반 Status 선택과 구분되는 버튼/이름을 사용하며, 증거나 필수 추가 입력이 필요한 경우 같은 모달로 유도하고 즉시 저장하지 않는다. |

Pass & Next 예외는 기존 동작 및 이미지 2를 유지하기 위한 설계 판단이다. 기본 두 입력 경로는 모두 모달을 사용하며, Failed 등 다른 상태에 무확인 즉시 저장 예외를 늘리지 않는다. 기존 Jump to next 설정이 모달의 명시적인 Save result / Save & Next 의도를 뒤집어서는 안 된다.

Status는 기본 표시 열이며 제목 옆에서 전체 라벨을 읽을 수 있어야 한다. 색만으로 구분하지 않는다. 390px에서는 불필요한 메타데이터를 먼저 줄이고 핵심 제목/Status 조작이 가로 스크롤 밖으로 사라지지 않게 한다. 이 메뉴는 행 전체 선택/체크박스 bulk 선택을 부수적으로 변경하지 않는다.

프로젝트에서 허용한 상태·권한·닫힌 Run 규칙을 재사용한다. 닫힌 Run/쓰기 권한 없음은 읽기 전용 상태이며, Untested 복귀를 새 기록처럼 추가하거나 기록을 덮어쓰는 기능은 도입하지 않는다.

## 6. 대상·초안·오류·포커스 계약

- 대화상자는 동시에 하나만 열린다. 열 때 `projectId/runId/testId`, 케이스 식별 문맥, 진입점과 복귀 포커스를 고정한다. 비동기 선택 변경으로 저장 대상이 바뀌면 안 된다.
- 행 B에서 열었는데 패널이 A를 보여주는 불일치를 방지한다. 열기 전에 선택 문맥을 B로 맞추되 실제 결과 상태는 저장 전까지 바꾸지 않는다. 필요한 데이터 로딩/실패를 빈 케이스로 대체하지 않는다.
- 입력 없는 Cancel/Escape/닫기는 즉시 닫고 원래 트리거로 포커스를 돌린다. 작성한 값/파일이 있으면 같은 창 내부의 간단한 폐기 확인으로 ‘계속 작성 / 초안 버리기’를 제공한다. 중첩 모달을 만들지 않는다. 배경 클릭은 자동 폐기하지 않는다.
- 저장 중에는 중복 제출과 다른 대상 열기를 막고 상태를 알린다. 닫기 제어로 요청이 취소됐다고 오인하게 하지 않는다. 새로고침/재진입 시 이미 서버에 생성된 결과를 초안으로 되돌리지 않는다.
- 결과 저장 실패는 입력과 파일을 보존하고 로컬 오류·Retry를 제공한다. 결과는 저장됐지만 첨부가 실패하면 그 사실을 분리 표시하고 창을 자동으로 닫거나 다음 테스트로 이동하지 않는다.
- 첨부 재시도는 UI-030/031의 동일 결과 ID를 재사용하고 성공 파일을 중복 업로드하지 않는다. 부분 성공 뒤의 Close/Discard는 이미 저장된 결과를 취소하지 않는다는 안내를 제공한다. 저장된 결과 내용의 변경은 첨부 재시도와 구분한다.
- 전체 성공 시 행 Status/이력/집계를 일치시키고 창을 닫는다. 원래 행이 필터에서 사라졌으면 접근 가능한 목록/다음 선택 대상으로 포커스를 옮기고 변화 이유를 알린다. 오류 시에는 트리거로 포커스를 빼앗지 않는다.
- portal/공통 overlay 계층, 배경 비활성화, 스크롤 잠금, 제목 연결, Tab/Shift+Tab 포커스 제한, Escape, 포커스 복귀를 구현·검증한다. 단순 `z-index` 변경이나 `role=dialog` 선언만으로 완료하지 않는다.

환경 때문에 필수 동작을 검증하지 못하면 `blocked`, 테스터 검토가 없으면 `pending`으로 기록한다. UI-031의 안전한 저장 거절 이력은 정상 첨부 흐름의 실검증을 대체하지 않는다. 레이아웃 변경의 시안/검토 조건은 상위 문서 §5.3을 따른다.

`docs/ux-evidence/UI-037.md`–`UI-039.md`에 fixture·동작·요청/저장 대상·검증 결과·캡처 경로를 기록하고 최종 답변에 핵심 전후 이미지를 첨부한다. 참고 이미지나 과거 캡처를 새 검증으로 사용하지 않는다.

## 10. 기존 문서와의 관계

- UI-011의 ‘Results 탭 내부 폼’은 당시 완료 이력으로 보존하되 목표 배치는 본 설계의 공통 모달로 대체한다.
- UI-051은 이전의 ‘Assign To 제외’, ‘Version/Elapsed 접기’, ‘세 개의 하단 버튼’, ‘실패 상태에서 Actual/Defects 동시 기본 노출’ 지침을 §3–5의 구체 배치로 대체한다. 저장/첨부 복구·필수 입력·명시적 다음 이동 의도는 보존한다. UI-037–039는 과거 전달 이력이며 UI-051을 자동 완료시키지 않는다.
- UI-010의 명시적인 Pass & Next 빠른 성공은 유지한다. 일반 Status 드롭다운의 Passed 즉시 저장은 UI-038에서 없앤다.
- UI-014/033의 밀도 목표 때문에 수행 지침을 숨겨서는 안 된다. UI-021 최종 검증에 두 진입점과 실제 수행 흐름을 포함한다.
- [전체 화면 재검토](./TESTRAIL_UI_REALIGNMENT_REVIEW_2026-09-19.md)에 따라 NEXT_ACTIONS 후보에 편성했다. UI-037 → UI-038 → UI-039 의존성을 지키고 각 단위가 Current batch로 승격될 때만 수행한다. 이 설계 문서가 Current batch를 직접 대체하지 않는다.
